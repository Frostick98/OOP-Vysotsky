## 1. Що реалізовано

Клас `CollectionUtils` з чотирма узагальненими методами: `Map`, `MaxBy`, `Filter`, `ForEach`. Поведінку (як перетворити, за яким ключем порівнювати, яку умову перевірити, що зробити з елементом) методи отримують через делегати `Func`, `Predicate` та `Action`. Робота демонструється на `List<Product>`, `List<int>` і `List<string>` з різними лямбда-виразами.

Рішення, прийняті під час реалізації:

- `Map` і `Filter` написані через `yield return`, тому виконуються відкладено, як `Select` і `Where` у LINQ. Перевірка аргументів на `null` виконується одразу під час виклику, а не під час перебору.
- `MaxBy` для порожньої колекції кидає `InvalidOperationException`, замість того щоб тихо повертати `default`. З прикладу методички це відрізняється, бо `default` для `int` дав би «максимум» 0, якого в колекції немає.
- Якщо кілька елементів мають однаковий максимальний ключ, `MaxBy` повертає перший з них.

## 2. Чому делегати корисні для створення таких утиліт?

Делегат дозволяє передати в метод поведінку як параметр. Алгоритм обходу колекції в `Map`, `Filter` чи `ForEach` завжди однаковий, а відрізняється лише те, що робити з елементом. Без делегатів довелося б писати окремий метод для кожного випадку: `GetNames`, `GetPrices`, `FilterExpensive`, `FilterEven` тощо. З делегатом один метод `Filter<T>` працює з будь-яким типом і будь-якою умовою. У поєднанні з узагальненнями (generics) це дає повторне використання коду без дублювання і без втрати типобезпеки: компілятор перевіряє типи і в самій колекції, і в лямбді.

## 3. Як лямбда-вирази спрощують виклик цих методів?

Лямбда-вираз дозволяє описати потрібну дію прямо на місці виклику. Без неї для кожної умови довелося б писати окремий іменований метод і передавати його в `Filter`:

```csharp
static bool IsExpensive(Product p) => p.Price > 1000;
var expensive = CollectionUtils.Filter(products, IsExpensive);
```

З лямбдою це один рядок:

```csharp
var expensive = CollectionUtils.Filter(products, p => p.Price > 1000);
```

Додатково лямбда:

- не потребує вказувати типи: компілятор сам виводить `TSource`, `TResult` і `TKey` з колекції та тіла лямбди (наприклад, `CollectionUtils.Map(products, p => p.Name)` повертає `IEnumerable<string>`);
- може використовувати локальні змінні навколишнього методу (замикання). У демонстрації `ForEach(numbers, n => sum += n)` накопичує суму у змінну `sum`, оголошену поза лямбдою.

## 4. Порівняння з вбудованими LINQ-операторами

| Власний метод | LINQ | Спільне | Відмінності |
|---|---|---|---|
| `Map` | `Select` | Відкладене виконання, однаковий результат (перевірено через `SequenceEqual`) | LINQ має додаткову перевантаження з індексом елемента та внутрішні оптимізації для масивів і списків |
| `Filter` | `Where` | Відкладене виконання, однаковий результат (перевірено через `SequenceEqual`) | LINQ використовує `Func<T, bool>`, а наш метод `Predicate<T>`. LINQ теж має версію з індексом |
| `MaxBy` | `Enumerable.MaxBy` (.NET 6+) | Знаходить елемент з максимальним ключем, перший за наявності рівних (перевірено через `ReferenceEquals`) | Наш метод вимагає `TKey : IComparable<TKey>`, LINQ приймає будь-який ключ і має перевантаження з `IComparer<TKey>`. Для порожньої колекції LINQ повертає `null` (reference-типи) або кидає виняток (value-типи), а наш метод завжди кидає `InvalidOperationException` |
| `ForEach` | `List<T>.ForEach` | Виконує дію для кожного елемента | Для `IEnumerable<T>` у LINQ такого оператора немає, а `List<T>.ForEach` працює лише зі списками. Наш метод працює з будь-якою колекцією |

Висновок: власні методи повторюють поведінку LINQ, але LINQ ширший, краще оптимізований і перевірений. Реалізація власних утиліт корисна для розуміння делегатів та відкладеного виконання (`yield return`), а у виробничому коді доцільніше користуватися LINQ.

## 5. Відповіді на контрольні запитання

1. **Чому делегати зручні для передавання поведінки в узагальнені методи?** Вони дозволяють винести змінну частину алгоритму в параметр, а сам алгоритм (обхід колекції) залишити в одному місці. Метод не знає, що саме він виконує, і тому підходить для будь-яких типів та умов.
2. **Різниця між `Func<T, TResult>`, `Action<T>` та `Predicate<T>`.** `Func<T, TResult>` приймає параметри і повертає значення довільного типу. `Action<T>` приймає параметри, але нічого не повертає (`void`). `Predicate<T>` приймає один параметр і завжди повертає `bool`, тобто це спеціалізований різновид `Func<T, bool>`.
3. **Переваги поєднання generic-методів і лямбда-виразів.** Один метод працює з різними типами і різною логікою, код стислий і читабельний, типи перевіряються на етапі компіляції, а лямбда може використовувати змінні навколишнього контексту.
4. **Коли власні утиліти корисні попри LINQ?** Для навчання; коли потрібна особлива поведінка (власні винятки, логування, негайне виконання); у проєктах, де LINQ недоступний або небажаний; для операцій, яких у LINQ немає чи які працюють інакше (наприклад, `ForEach` для будь-якого `IEnumerable<T>`).
